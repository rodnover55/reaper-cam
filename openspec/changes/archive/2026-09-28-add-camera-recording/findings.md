# Результаты разведки

Ответы на вопросы из design.md — D10. Проверено на REAPER 7.80/linux-x86_64:
звук через PulseAudio (сервер PipeWire), 44.1 кГц, блок 512 сэмплов. REAPER
сообщает для PulseAudio задержку ввода около 85 000–89 000 сэмплов (≈ 2 с) и
вывода 3 000–9 000 сэмплов; значения плавают от вызова к вызову.

Проверки шли через отладочную сборку: журнал `reaper-cam.log` в каталоге
ресурсов REAPER, отладочные действия `_REAPER_CAM_DEBUG_*` и тестовый источник
кадров. Числа с кадров в окне видео REAPER читались по полосам клеток тестового
источника, снимком окна через X11.

## Вопрос 1. Формат в Track recording settings и программное назначение

**Программное назначение работает.** Блок

```
<RECCFG 1
bWFjcg==
>
```

в состоянии дорожки (сразу после `NCHAN`) назначает дорожке формат расширения:
при записи REAPER зовёт `CreateSink` с конфигурацией из четырёх байтов — кода
формата. `bWFjcg==` — base64 от байтов `macr`, то есть
`REAPER_FOURCC('r','c','a','m')` в памяти. Код формата стоит в первых четырёх
байтах конфигурации, как у MP3 из SDK (`pcmsink_mp3lame.cpp`), и по нему REAPER
выбирает формат.

Число после `<RECCFG` REAPER пишет сам: `<RECCFG 0` с конфигурацией WAV
проекта появилось, когда действие 40604 отработало без показа окна (осталась
точка отмены «Adjust track recording settings»).

**Формат виден в Track recording settings, и выбор в окне работает.** Список
форматов окна (действие 40604) — WAV, AIFF, CAF, FLAC, MP3 (encoder by LAME
project), OGG Opus, OGG Vorbis, **Video (camera)**, WavPack lossless
compressor, Raw PCM data. Путь пользователя проверен от начала до конца:
галочка «Set recording audio format», в списке «Video (camera)», окно
закрывается — в состоянии дорожки появляется `<RECCFG 1 bWFjcg==>`. Число
после `<RECCFG` — эта галочка: 0 — формат проекта, 1 — свой.

Устройство окна, важное для задачи 6.5:

- Кнопок OK и Cancel нет, выбор применяется при закрытии окна крестиком.
  `WM_CLOSE` и `IDOK`, посланные окну, выбор не применяют.
- При выборе формата REAPER зовёт `ShowConfig` с окном Track recording settings
  в роли родителя и встраивает возвращённое окно в рамку «Format». Если
  `ShowConfig` окна не создаёт, выбор не применяется вовсе: конфигурацию
  REAPER берёт у этого окна.
- Конфигурацию REAPER забирает сообщением `WM_USER + 1024` в два захода:
  сначала `wParam` — указатель на `int` под длину, `lParam` = 0; потом
  `wParam` = 0, `lParam` — буфер под байты. Длину можно отдавать любую.

Как проверялось. Окно не показывается, если REAPER не в фокусе, а фокус на
общем рабочем столе у пользователя. Отладочный наблюдатель на таймере
расширения ловит окно на первом тике после действия 40604, пишет в журнал
его контролы и пункты списков, ставит галочку и выбирает формат; закрывалось
окно событием X11, как от крестика.

**Экземпляр без записи.** Когда формат меняется у дорожки, стоящей на
записи, REAPER сразу создаёт экземпляр с настоящим именем файла записи. Этот
экземпляр живёт без единого сэмпла, а при нажатии Record REAPER уничтожает
его, удаляет его файл и создаёт новый экземпляр для записи. Создание
экземпляра — не начало дубля: дубль начинается с первого `WriteDoubles`.

**`PCM_SINK_EXT_GIVE_TRACK_HINT` не приходит** ни при одной записи: экземпляр
не знает своей дорожки. Камера дорожки берётся из конфигурации формата
(design.md D2).

Регистрация `plugin_register("pcmsink_ext", …)` возвращает 1.

## Вызовы экземпляра при обычной записи

Запись дорожки в режиме «вход», 5 секунд:

| Что | Как |
|---|---|
| `CreateSink` | главный поток, в момент Record; `nch` — число каналов входа дорожки (1 для Input 1), `srate` — частота проекта, `buildpeaks` = true |
| Имя файла | `<папка записи проекта>/01-cam-<ггммдд>_<ччмм>.<расширение из GetExtension>` |
| `SETCURBLOCKTIME` | перед каждым `WriteDoubles` |
| `WriteDoubles` | блоками по 512 сэмплов, первый блок неполный (201 сэмпл); из рабочих потоков REAPER, не из главного, пачками |
| После Stop | `Extended(PCM_SINK_EXT_CREATESOURCE)`, затем уничтожение — оба в главном потоке |
| `GetLength` | за запись дважды, из главного потока |

`SETCURBLOCKTIME` сообщает **позицию воспроизведения блока**, а не позицию
записанных сэмплов. Первый блок пришёл с позицией 2.078 с при записи с 0.0:
разница — задержки ввода и вывода, которые REAPER сам вычитает при записи
входа.

На `PCM_SINK_EXT_CREATESOURCE` экземпляр отвечает 0 — и REAPER сам создаёт
источник по файлу: для MOV и Matroska — видео (`VIDEO`), для пустого файла —
`WAVE` нулевой длины.

После Stop окно «Select files to save or delete» (включённая у пользователя
настройка «Prompt to save/delete/rename new files: on stop») показывает файл
видео наравне со звуковыми. Проверки останавливают запись действием 40667
«Transport: Stop (save all recorded media)», которое этого окна не показывает.

## Вопрос 6. Контейнер

Запись 5 секунд тестового источника 640×360, 30 кадров в секунду, в каждый
кандидат. Айтем REAPER поставил на начало записи (0.0), длиной — сколько
сэмплов получил экземпляр (`GetLength`).

| Контейнер | Тип тейка | Длина айтема | Длина источника | Кадров | Кадр при курсоре 2.5 с |
|---|---|---|---|---|---|
| MOV, Photo-JPEG | VIDEO | 4.789 | 4.800 | 144 | file 2.500 |
| MOV фрагментированный | VIDEO | 5.155 | 5.167 | 155 | file 2.500 |
| Matroska | VIDEO | 4.991 | 5.000 | 150 | file 2.500 |

Во всех трёх окно видео REAPER показывает кадры, и время файла на кадре равно
расстоянию от начала айтема до курсора (проверено в точках 0.5, 2.5 и 4.7 с
для MOV, 2.5 с для остальных). Позиция шкалы, рассчитанная как «позиция блока
минус задержки ввода и вывода», отстаёт от курсора на 12 мс в MOV и на 4 мс в
Matroska — меньше половины кадра, без дрейфа.

**Файл после аварии.** Писатель не закрыт, последние 5000 байт обрезаны:

| Контейнер | REAPER | ffprobe |
|---|---|---|
| MOV | `WAVE`, длина 0 — запись потеряна | moov atom not found |
| MOV фрагментированный, длительности только при закрытии | `VIDEO`, длина 0 | 90 кадров, 3.0 с |
| MOV фрагментированный, длительности после каждого фрагмента | `VIDEO`, длина 3.000 | 90 кадров, 3.0 с |
| Matroska | `VIDEO`, длина 30.000 (выдуманная) | 89 кадров |

REAPER берёт длину фрагментированного MOV из заголовка и фрагменты не
пересчитывает. Поэтому писатель обновляет длительности (`mvhd`, `tkhd`,
`mdhd`, `mehd`) после каждого целого фрагмента.

**Выбор: фрагментированный MOV с кодеком Photo-JPEG, фрагмент — секунда,
длительности обновляются после каждого фрагмента.** Проверка на macOS —
вместе с её захватом (design.md — Risks).

## Вопросы 2 и 3. Режимы записи REAPER

Две дорожки пишут вход с выключенным мониторингом: `cam` — в формат
расширения (фрагментированный MOV), `audio` — в WAV проекта, для сравнения.
Запись с 10.0 с, 120 BPM, 4/4. Звук с задержкой ввода ≈ 2 с (PulseAudio),
поэтому звук последних двух секунд перед Stop REAPER не пишет ни в один файл —
айтемы короче времени записи.

| Режим | Экземпляров | Что пришло в экземпляр | Где REAPER поставил айтемы |
|---|---|---|---|
| Обычная запись | 1 | блоки с позиций 12.18…13.89, 1.718 с сэмплов | видео и звук: 10.000, длина 1.718 |
| Pre-roll 2 такта | 1 | сэмплы и во время пре-ролла: блоки с 8.10 (6.0 + задержка), 5.875 с | видео и звук: 10.000, длина 1.869, смещение тейка 4.005 |
| Count-in 2 такта | 1, создан по Record до отсчёта | во время отсчёта ничего; блоки с 12.08 | видео и звук: 10.000, длина 1.896, смещение 0 |
| Auto-punch по выделению 12–14 | 1 | всё с начала записи: блоки с 12.08, 4.976 с | видео и звук: 12.000, длина 2.000, смещение 2.000 |
| Auto-punch по айтемам 12–14 | 1 | то же, что по выделению | видео и звук: 12.000, длина 2.000, смещение 2.000; выделенные пустые айтемы заменены |
| Петля 10–12, три с лишним прохода | 1 на все проходы | один непрерывный поток, 7.020 с; позиции блоков ходят по кругу в пределах петли | видео и звук: айтем 10–12 с четырьмя тейками (смещения 0, 2.074, 4.0, 6.0) и айтем 12.000–12.074 — у видео и звука одинаково |
| Пауза 3 с | 1 на всю запись | во время паузы сэмплов нет; после продолжения позиции блоков откатываются назад примерно на задержку вывода (14.075 → 13.917) | видео и звук: один сплошной айтем 10.000–16.075 |
| Stop (DELETE all recorded media) | 1 | как при обычной записи; `CREATESOURCE` приходит и здесь | айтемов нет, файлы видео и звука удалены самим REAPER после уничтожения экземпляра |
| Undo после записи | 1 | как при обычной записи | айтемы видео и звука исчезли вместе, файлы остались на диске — как у звука |

**Вопрос 2.** `SETCURBLOCKTIME` приходит перед каждым `WriteDoubles` во всех
режимах. Позиция — позиция обработки блока, то есть не позиция записанного:
при записи входа записанное стоит на задержку ввода и вывода раньше. В
пре-ролле позиции идут с начала пре-ролла, при count-in — с начала записи,
в петле — по кругу внутри петли. После паузы позиция обработки продолжается
с позиции, которую было слышно в момент паузы, — назад на задержку вывода.

**Вопрос 3.** Экземпляр один на запись во всех режимах: и на все проходы
петли, и через паузу. Во время паузы сэмплов нет. При auto-punch и пре-ролле
экземпляр получает всё с начала записи, а REAPER сам ставит айтем на участок
punch-in и отрезает лишнее смещением тейка. Все дубли петли — тейки одного
файла с разными смещениями.

Во всех режимах видео-айтем совпал со звуковым по позиции, длине, смещению
тейка и числу тейков. Кадр, вынутый из файла на время t, стоит на шкале в
«начало айтема + (t − смещение тейка)» — по той же формуле REAPER показывает
видео в окне (проверено в 2.5). Время файла, то есть счёт сэмплов, — общая
ось видео и звука: сэмпл номер n и место сетки с моментом n / частота лежат
на шкале в одной точке.

Позиция шкалы, рассчитанная упрощённо — «позиция блока минус задержки ввода
и вывода на момент CreateSink», — отстаёт от настоящей на 8–12 мс; в петле она
сдвинута на длину петли, а после паузы — ещё на 170 мс. Для размещения кадров
позиция блока поэтому не годится: связь с временем файла строится по счёту
сэмплов (design.md D4), а мост часов должен начинать отсчёт заново после
паузы и после скачка позиции.

## Вопрос 4. Режим записи дорожки-камеры

Запись 4 секунд с 10.0 с в каждом режиме записи дорожки, `cam` и `audio` в
одном и том же режиме, мониторинг выключен.

| Режим записи дорожки | `I_RECMODE` | Экземпляр | `nch` | Первый блок | Где стоит записанное | Длина айтема |
|---|---|---|---|---|---|---|
| Вход, Input 1 | 0 | да | 1 | 12.08 | позиция блока − (ввод + вывод) | 1.7–1.9 |
| Вход, без входа | 0, `I_RECINPUT` −1 | нет | — | — | — | айтемов нет |
| Выход стерео | 1 | да | 2 | 10.00 | ровно на позиции блока | 4.087 |
| Выход моно | 5 | да | 1 | 10.00 | ровно на позиции блока | 4.052 |
| Выход стерео с компенсацией задержки | 3 | да | 2 | 12.08 | позиция блока − (ввод + вывод) | 2.004 |
| Выход моно с компенсацией задержки | 6 | да | 1 | 12.08 | позиция блока − (ввод + вывод) | 2.005 |
| None (только мониторинг) | 2 | нет | — | — | — | айтемов нет |

Во всех режимах, где экземпляр создаётся, айтем начинается на позиции начала
записи, смещение тейка 0, видео совпадает со звуком.

**Без физического входа экземпляр создаётся в режимах записи выхода** —
стерео и моно, с компенсацией задержки и без. Режим «вход» без входа и режим
«none» экземпляра не дают.

**Сдвиг на задержки.** При записи входа и в режимах выхода «с компенсацией
задержки» REAPER ставит записанное на задержку ввода и вывода раньше позиции
блока — и теряет в конце дубля столько же (при PulseAudio это 2 с). В режимах
выхода без компенсации записанное стоит ровно там, где блок обрабатывался, и
ничего не теряется.

**Режим дорожки-камеры — «выход (моно)», `I_RECMODE` 5.** Физический вход не
нужен, запись начинается сразу и заканчивается со Stop, а данных копируется
вдвое меньше, чем в стерео. Кадр переводится во время файла через задержку
вывода: место сетки с моментом n / частота — это блок, обработанный на
позиции P, а слышна эта позиция на задержку вывода позже; кадр, снятый в
момент T, ложится туда, что было слышно в T (design.md D5).

## Вопрос 5. Экземпляр не создался

`CreateSink` дорожки-камеры отказывает и сообщает причину через
`SetRenderLastError`; вместе с ней на записи звуковая дорожка.

- REAPER зовёт `CreateSink` дважды подряд, оба раза получает отказ.
- **Запись не начинается вовсе**: транспорт остаётся в стопе, звуковая
  дорожка не записана, файлов нет.
- REAPER показывает модальное окно «REAPER Recording Error: Can't write to
  recording files, does the directory exist?». Текст из `SetRenderLastError`
  в нём не показан.

Отсюда политика ошибок (design.md D11): экземпляр создаётся всегда. Если
камера недоступна, он пишет чёрный кадр, а причина с именем камеры уходит в
консоль REAPER.

## Вопрос 7. Поток `WriteDoubles` и сопоставление с аудиохуком

Отладочный аудиохук (`Audio_RegHardwareHook`) кладёт в кольцевой буфер без
блокировок отметку каждого блока: монотонное время, `GetPlayPosition2Ex`,
состояние транспорта, длину блока. Таймер переписывает отметки в журнал.
Запись 3 секунд дорожки-камеры в режиме «выход (моно)»:

- Аудиохук зовётся из одного потока — звукового.
- **`WriteDoubles` REAPER зовёт из своих рабочих потоков**: за 3 секунды — из
  десяти разных, ни разу из звукового и ни разу из главного. Вызовы идут
  пачками.
- Блоков записи у аудиохука 256, у экземпляра 256. **Позиции из
  `SETCURBLOCKTIME` совпадают с `GetPlayPosition2Ex` блоков аудиохука один к
  одному и в том же порядке**, первый — 10.0, позиция начала записи.
- `SETCURBLOCKTIME` приходит позже блока аудиохука на 0.1–43 мс, медиана
  19 мс: время вызова `WriteDoubles` для часов не годится.

**Правило сопоставления.** Блок экземпляра — это следующий блок записи
аудиохука с той же позицией. Порядок нужен, потому что позиции не
уникальны: в петле они повторяются на каждом проходе, после паузы
откатываются назад (вопрос 3). Счёт сэмплов экземпляра на начало блока — время
файла, монотонное время блока аудиохука — момент, когда блок обрабатывался.
Эти пары и есть вход моста часов (design.md D5). В режиме «выход» без
компенсации (вопрос 4) слышно этот блок на задержку вывода позже.

## Итог: что меняется в design

| Вопрос | Решение | Где в design |
|---|---|---|
| Контейнер | Фрагментированный QuickTime с кодеком Photo-JPEG, фрагмент — секунда; длительности в индексе обновляются после каждого фрагмента. Обычный MOV и Matroska убираются | D7 |
| Режим записи дорожки-камеры | «Выход (моно)», `I_RECMODE` 5, мониторинг выключен | D3 |
| Сопоставление сэмплов с аудиохуком | Блок экземпляра — следующий блок записи аудиохука с той же позицией (`SETCURBLOCKTIME` = `GetPlayPosition2Ex`); время файла блока — счёт сэмплов на его начало, монотонное время — отметка аудиохука; поправка — задержка вывода по слышимой позиции хоста у каждого блока (раздел «Задержка вывода»); после паузы мост строится заново | D5 |
| Политика ошибок | Экземпляр создаётся всегда: отказ `CreateSink` срывает всю запись. Недоступная камера — чёрный кадр и сообщение в консоль | D11 |
| Назначение формата | Как задумано: Track recording settings; запасное действие не нужно | D1 |

Что ещё выяснилось и учитывается в реализации:

- `WriteDoubles` приходит из разных рабочих потоков REAPER, `GetLength` — из
  главного, одновременно с ними. Счётчик сэмплов экземпляра — атомарный
  (D8).
- REAPER создаёт экземпляр и без записи — при смене формата у дорожки на
  записи — и уничтожает его без сэмплов, удаляя файл. Создание экземпляра
  дешёвое и не открывает камеру: камеру открывает arm (D3).
- Экземпляр не знает своей дорожки: `GIVE_TRACK_HINT` не приходит (D2).
- Stop с удалением, undo, дубли петли, auto-punch и пре-ролл REAPER
  отрабатывает сам по файлу экземпляра — расширению делать ничего не нужно
  (D1).

## Дрожание аудиохука на этой машине

Отметки аудиохука из записи для вопроса 7 (PulseAudio, 44.1 кГц, блок 512):
REAPER обрабатывает звук пачками — между соседними вызовами от 0.02 до
163 мс при среднем 11.07 мс. Отклонение отметок от прямой «монотонное время ↔
позиция» — до ±100 мс (СКО 47 мс) при наклоне 0.9968: за 3 секунды пачки
не усредняются. С настоящей звуковой картой через ALSA пачек не бывает, и
дрожание — в пределах блока.

Мост часов усредняет пары в окне вокруг момента и так проводит прямую через
середину пачек (раздел «Задержка вывода»). Насколько устойчив остаток при
PulseAudio — видно по хлопку (задача 7.2).

## Задержка вывода (задача 6.2)

Дорожка-камера пишет выход (design.md D3), и кадр должен лечь туда, что звучало
в момент съёмки. Проверялось тестовым источником отладочной сборки: он рисует
на кадре слышимую позицию REAPER (`GetPlayPosition`) в момент съёмки, а
расширение отмечает каждый блок аудиохука — момент, позицию обработки
(`GetPlayPosition2Ex`) и слышимую позицию (`GetPlayPositionEx`). PulseAudio,
44.1 кГц, блок 512.

**Задержка вывода плавает.** Разница «позиция обработки − слышимая позиция» —
это задержка вывода, по которой REAPER считает слышимое. За один дубль её
медиана по секундам менялась от 233 до 176 мс, в другом дубле держалась около
140–170 мс, а `GetInputOutputLatency` в конце дублей этой проверки сообщал
задержку вывода от 62 до 226 мс. Снимок при создании экземпляра поэтому
ошибается на десятки миллисекунд.

**Как ведёт себя слышимая позиция REAPER:**

- После Record и после продолжения с паузы REAPER держит её на месте, пока
  звук записи не дошёл до выхода, — 150–340 мс; обработка тем временем идёт:
  первые 15 блоков обрабатываются сразу, пачкой.
- В начале дубля она сходится несколько секунд: сдвиг «слышимая позиция −
  монотонное время» уходит на 60 мс за 6 с, хотя обработка идёт ровно —
  верхняя огибающая пачек стоит на месте.
- Дальше — блуждание ±17 мс с периодом около 9 с и дрожание со СКО 10–14 мс;
  отдельные значения отходят до ±40 мс.
- Наклон за 40 с — 1.00004: часы звуковой карты и монотонные расходятся на
  десятки миллионных долей.

**Как кадр переводится во время файла.** Пара моста — момент блока и время
файла, которое звучало в этот момент: время файла блока минус «позиция
обработки − слышимая позиция». Пока слышимая позиция стоит, пары в мост не
идут. Время файла кадра — момент съёмки плюс средний сдвиг пар в окне 1 с
вокруг него, без выбросов дальше четырёх медианных отклонений; наклон — 1.
Писатель ставит кадр, когда пары после него заполнили полокна, и отстаёт от
записи примерно на 0.6 с. Кадр, снятый до первой пары, переводится по прямой
назад и может достаться месту 0; кадры, снятые после Stop, пока звучало
обработанное, — по прямой вперёд: писатель ждёт их до момента, когда прозвучал
бы конец файла.

Отвергнуто по замерам:

- **Мост по позиции обработки и снимок задержки** — ошибка равна уходу
  задержки, десятки миллисекунд.
- **Наименьшие квадраты за 10 с** — оценка наклона по дрожащим парам за
  секунды ошибается на проценты (1.0116 за 6 с), а длинное окно отстаёт от
  схождения слышимой позиции в начале дубля: места уходили на 20–60 мс.
- **Окно только за моментом** — то же отставание, до 44 мс в первую секунду.

**Результат по режимам из 2.6.** «Место − слышимое» — время файла места сетки
минус время файла, которое звучало в момент съёмки кадра по сглаженной
слышимой позиции; предел — округление до места сетки, ±16.7 мс при 30 кадрах.
«Место − нарисованное» — то же на шкале против позиции, нарисованной на кадре:
в ней вся дрожь REAPER.

|---|---|---|---|---|

- **Петля.** Первое место прохода может получить последний кадр прошлого

- **Пауза.** После продолжения REAPER обрабатывает с позиции, которую было
  слышно в момент паузы (откат на задержку вывода, здесь 0.37 с), а время файла
  продолжается — и REAPER показывает всё записанное после паузы на этот откат
  позже, звук тоже (раздел «Вопросы 2 и 3»: после паузы позиция шкалы
  сдвинута ещё на 170 мс). Видео идёт по времени файла и остаётся со звуком
  (сценарий «Пауза» в `camera-recording`); отрезок файла, который обработан до
  паузы, но так и не прозвучал, показывает последний кадр до паузы и первый
  после.
- **Pre-roll и петля при записи выхода.** Дорожка-камера пишет выход, звуковая
  дорожка в этих прогонах — вход с компенсацией задержки. Поэтому пре-ролл до
  экземпляра не доходит (у звука смещение тейка 4.005, у видео 0), а у звука
  в петле смещения дублей 0, 2.072, 4, 6 и отдельный айтем 12.000–12.072, у
  видео — 0, 2, 4, 6, 8. Расхождение — задержка ввода PulseAudio, около 2 с;
  с настоящей камерой и обычной звуковой картой это проверяет задача 7.1.

## Аудиохук и arm (задачи 6.3, 6.4)

**Задержки от arm не меняются.** `GetInputOutputLatency` раз в 0.1 с, по 40
отсчётов, трижды попеременно без arm и с arm дорожки-камеры: медианы задержки
ввода 1939–1968 мс, вывода 134–162 мс в обоих состояниях; внутри каждой серии
задержка вывода и так ходит от 42 до 220 мс.

**Выпадения.** Счётчика выпадений на этой машине REAPER не ведёт:
`GetUnderrunTime` возвращает нули даже после того, как процесс REAPER
остановлен на 0.4 с посреди воспроизведения. Поэтому две записи по 10 минут —
с дорожкой-камерой (тестовый источник) и без неё — сравнивались по самому
аудиохуку:

| Запись 10 мин | Блоков аудиохука | Шаг позиции не 512 сэмплов | Потеряно отметок кольцом | Самый длинный промежуток между вызовами |
|---|---|---|---|---|
| с дорожкой-камерой | 51 680 (ожидалось 51 668) | 0 | 0 | 164 мс |
| без неё | 51 678 (ожидалось 51 674) | 1 | — | 46 мс |

Разница в промежутках — от PulseAudio, а не от камеры: четыре записи по 30 с
подряд, попеременно с камерой и без, дали одинаковые 43 мс. Пачки PulseAudio
меняются от сеанса к сеансу (раздел «Дрожание аудиохука»).

Десятиминутное видео: 18 001 место на 600.033 с, «место − слышимое» по
минутам — среднее от −2.8 до −5.4 мс, наибольшее 19 мс, без роста к концу.

**Прогрев по arm.** Поверхность управления (`csurf_inst`) на
`SetSurfaceRecArm` и `SetTrackListChange` пересчитывает поставленные на запись
дорожки-камеры. Проверено `fuser /dev/video0` с настоящей камерой:

| Действие | REAPER держит `/dev/video0` |
|---|---|
| arm дорожки-камеры из скрипта | да; режим записи стал 5, мониторинг выключен |
| снятие arm | нет |
| выделение дорожки с «Automatic record-arm when track selected» | да — REAPER ставит arm сам, с задержкой до секунды |
| выделение другой дорожки | нет — arm снят сам |
| открытие проекта с поставленной на запись дорожкой-камерой | да, через 0.8 с после загрузки |

Флаг автоматического arm у дорожки в API — `B_AUTO_RECARM`.

## Окно настроек формата (задача 6.5)

Окно — список камер и список режимов MJPEG выбранной камеры, под ними строка
сообщения. Камеры перечисляются заново при каждом открытии. Камера без MJPEG
стоит в списке с пометкой «(no MJPEG)», выбрать её нельзя: список
возвращается к прежней камере, а строка объясняет почему. Сохранённая камера,
которой нет в системе, остаётся в списке с пометкой «(not connected)» и
своим режимом — выбор не теряется. Если камера не сохранена, выбирается первая
с MJPEG и её самый крупный режим.

Проверено в Track recording settings отладочной сборки:

- в списке одна настоящая камера — «Integrated_Webcam_HD» (узла метаданных
  нет) — и отладочная «Test pattern (debug)»; режимы — только MJPEG: 1280x720,
  960x540, 848x480, 640x480, 640x360, все 30 fps;
- выбор 640x360 после закрытия окна крестиком записан в дорожку, проект
  сохранён, REAPER перезапущен с ним: у дорожки та же конфигурация, окно
  показывает ту же камеру и 640x360; смена на 960x540 так же применилась.

REAPER забирает конфигурацию у окна формата (`WM_USER + 1024`), только когда
окно Track recording settings закрывается по-настоящему — крестиком или
потерей фокуса, — и тогда же, когда формат в списке не менялся. Поддельные
`WM_ACTIVATE`, `WM_CLOSE` и `IDOK` окно не закрывают (раздел «Вопрос 1»).
Сообщение о камере без MJPEG проверено тестом: такой камеры на машине нет.

## Ошибки камеры (задача 6.6)

Сообщения уходят в консоль REAPER с приставкой «reaper-cam:» и именем камеры
из конфигурации дорожки. Проверено:

| Случай | Сообщения | Дубль |
|---|---|---|
| Камеру держит `ffmpeg -f v4l2 -i /dev/video0 -f null -`, arm и запись | при arm: `camera "Integrated_Webcam_HD" is not available (busy)`; при записи: то же и `: black frame until the end of the take` | видео — 119 чёрных кадров, звуковая дорожка записана |
| Камеру освободили, arm сняли и поставили снова | нет | камера открылась при повторном arm, в видео 119 кадров с изображением |
| Потеря камеры посреди дубля (отказ тестовой камеры по команде) | одно: `camera "Test pattern (debug)" is not available (test camera failure): black frame until the end of the take` | 117 кадров с изображением — 2.8 с до отказа и секунда повтора, — затем 95 чёрных до конца |
| Сохранённой камеры нет в системе, arm | `camera "USB Camera" is not available (not connected)` | — |

Потерянный захват заново открывается при следующем arm и при Record: камеру
могли освободить или подключить. При смене списка дорожек — нет, иначе
занятая камера сообщала бы о себе при каждой правке проекта. Потерю во время
записи сообщает только дубль, поверхность управления её лишь отмечает — так
на дубль одно сообщение. Отключить встроенную камеру посреди дубля без прав
администратора нельзя, поэтому потеря проверялась отказом тестовой камеры;
путь от ошибки устройства до чёрного кадра у них общий (реестр устройств).

## Захват на этой машине (задачи 5.1, 5.3)

Камера ноутбука — «Integrated_Webcam_HD», два узла: `/dev/video0` (видео,
`V4L2_CAP_VIDEO_CAPTURE`) и `/dev/video1` (метаданные,
`V4L2_CAP_META_CAPTURE`). V4L2 отдаёт имя обрезанным до 32 байт —
«Integrated_Webcam_HD: Integrate»; полное имя — строка продукта USB в sysfs.
Устойчивые ссылки есть и в `/dev/v4l/by-id` (с серийным номером), и в
`by-path`. Форматы — MJPG и YUYV; режимы MJPEG: 1280×720, 960×540, 848×480,
640×480, 640×360, все 30/1.

Захват 5 секунд 1280×720 @ 30/1 (`cam_probe capture`):

| «Exposure, Dynamic Framerate» | Кадров | Частота камеры | Пропуски по номерам кадров | Байты в файле |
|---|---|---|---|---|
| включено (так настроено у пользователя), ночь | 70 | 14 в секунду | — | совпали все |
| выключено | 143 | 28.5 в секунду | 1 из 144 | совпали все |

ниже номинальной. Обе вещи сетка кадров закрывает повтором (design.md D4).
Расширение настройку камеры не трогает.

## Время съёмки от камеры (задача 5.4)

Камера ноутбука присылает PTS и SCR в каждом заголовке пакета: за 4 секунды
около 14 000 заголовков, у всех есть и то и другое. Узел метаданных —
`/dev/video1`, формат `V4L2_META_FMT_UVC`.

**Номер кадра шины из SCR с номером хоста не сходится.** Связь по номеру
кадра шины (часы камеры → номер кадра по SCR → время хоста по номеру кадра в
приписке драйвера; так же делает драйвер при `hwtimestamps=1`) давала то +36
мс, то −362, то −580 мс от метки буфера. Разница «номер кадра хоста − номер
кадра камеры» по модулю 2048 в разных сеансах: 36, 1468 (то есть −580) —
камера нумерует кадры шины своим счётчиком со случайным от сеанса к сеансу
сдвигом.

**Связь по нижней огибающей.** Пакет не может быть обработан хостом раньше,
чем передан, поэтому по парам «SCR — момент обработки пакета» истинная связь
часов камеры с монотонными — нижняя огибающая: прямая по нижним 10 % точек,
опущенная на их 2-й процентиль. Номера кадров шины не нужны.

| Сеанс | Часы камеры | Кадров со временем от камеры | Начало съёмки раньше метки буфера |
|---|---|---|---|
| 1 | 15.000 МГц | 54 из 54 | 2.00 мс, СКО 1.28 мс |
