# Design

## Context

Мотивация — см. `proposal.md` — Why. Проект пустой: кроме каркаса OpenSpec в нём
ничего нет. Сборка, проверки и раскладка библиотек берутся по образцу соседнего
`reaper-tabs`.

Что задаёт рамки:

- **REAPER записывает через sink.** Формат записи проекта в API описан как
  «base64-encoded sink configuration» (`GetSetProjectInfo_String`,
  `RECORD_FORMAT`). Формат можно задать отдельной дорожке в Track recording
  settings; он хранится в состоянии дорожки блоком `<RECCFG>` (строка есть в
  бинарнике REAPER). В руководстве 7.80 (§3.39) среди форматов дорожки названы
  MP3 и Video (GIF). Оба регистрируют модули, а не ядро REAPER: MP3 —
  `reaper_mp3dec` (его исходник лежит в SDK), GIF — `reaper_video.so`. Формат
  расширения регистрируется тем же путём (`pcmsink_ext`, `reaper_plugin.h:947`).
- **Экземпляр sink видит запись изнутри.** `CreateSink` получает имя файла,
  число каналов и частоту. Перед каждым блоком приходит позиция проекта
  (`PCM_SINK_EXT_SETCURBLOCKTIME`, `reaper_plugin.h:932`), дорожка — через
  `PCM_SINK_EXT_GIVE_TRACK_HINT` (`:935`). Ошибку создания можно показать
  через `SetRenderLastError`. Когда и из какого потока REAPER делает эти вызовы
  при записи, SDK не говорит — это вопросы разведки (D10).
- **Arm и часы доступны расширению.** `IReaperControlSurface`
  (`reaper_plugin.h:1469`), зарегистрированный через `csurf_inst`, получает
  `SetSurfaceRecArm` (`:1492`) и `SetTrackListChange` (`:1486`).
  `Audio_RegHardwareHook` вызывает расширение на каждый аудиоблок в звуковом
  потоке. Позицию блока даёт `GetPlayPosition2Ex`, задержки —
  `GetInputOutputLatency`.
- **Видео REAPER открывает по-разному на разных ОС.** На Linux — через
  системный FFmpeg: `reaper_video.so` знает libavcodec версий 54–63. На macOS
  по умолчанию — через AVFoundation, которая не открывает MKV. Проверить в этом
  изменении можно только Linux.
- **Камера на Linux.** Встроенная камера работает по UVC, отдаёт MJPEG до
  1280×720 и YUYV до 640×480. У неё два узла: `/dev/video0` (видео) и
  `/dev/video1` (метаданные). Драйвер uvcvideo по умолчанию ставит кадру метку в
  момент прихода первого пакета. Перевод времени камеры в системное
  (`uvc_video_clock_update`) выключен параметром `hwtimestamps=0`, и включить
  его можно только с правами root. Узел метаданных (`V4L2_META_FMT_UVC`)
  отдаёт для пакетов время прихода в `CLOCK_MONOTONIC`, номер кадра шины USB
  (SOF) и заголовок UVC с полями PTS и SCR — по ним время съёмки
  восстанавливается без root. ffmpeg (libavdevice) узел метаданных открыть не
  может.
- **Решения пользователя из обсуждения** записаны в specs: кроссплатформенное
  устройство кода, никакой ручной работы, поправки только с известным
  направлением, звук не хуже, чем без видео, без предпросмотра, файл
  открывается в REAPER штатно.

## Goals / Non-Goals

**Goals:**

- Смысл записи — позицию, обрезку, дубли, паузу, удаление, undo — определяет
  REAPER. Расширение только поставляет данные.
- Всё, кроме модуля захвата Linux и модуля расширения, собирается и
  проверяется без REAPER, без камеры и без заголовков ОС.
- В звуковом потоке нет ничего, что может ждать.
- Разведка отвечает на вопросы о поведении REAPER до того, как пишется захват
  камеры.

**Non-Goals:**

- Общая библиотека контейнеров: писатель знает одну дорожку MJPEG с ровной
  частотой.
- Кодирование и декодирование видео, кроме одного заранее сжатого чёрного кадра.
- Совместное использование камеры с другими программами: камера открывается
  монопольно.
- Режимы записи MIDI на дорожке-камере.
- Поправка на половину выдержки. В автоэкспозиции камера сообщает выдержку
  ненадёжно, значит её величина не известна наверняка, и поправка по правилу
  `recording-sync` нулевая.

## Decisions

### D1. Запись идёт через собственный формат записи

Расширение регистрирует формат «видео с камеры» через `pcmsink_ext`. REAPER
создаёт экземпляр этого формата для каждой дорожки-камеры при каждой записи, а
после Stop сам создаёт айтемы и дубли, обрезает по auto-punch, удаляет файлы при
остановке с удалением, ведёт undo, называет и кладёт файл по своим настройкам.
Растущий во время записи айтем REAPER, судя по интерфейсу, рисует по данным
экземпляра: `GetLength` — «length in seconds, so far».

Почему так: все режимы записи REAPER работают без единой строки расширения, и
расхождение с REAPER исключено по построению.

Отвергнуто:

- **Слушать транспорт и вставлять айтемы самим** (`SetPlayState`, аудиохук и
  API айтемов). Каждый режим записи пришлось бы повторять, и любое отличие от
  REAPER давало бы рассинхрон.
- **Айтем-носитель с подменой источника.** Временные звуковые файлы и
  неочевидное поведение undo.

Разведка подтвердила путь целиком (`findings.md`, вопросы 1, 3, 5):

- формат «Video (camera)» есть в списке Track recording settings; выбор
  применяется при закрытии окна и пишет в дорожку `<RECCFG 1` с конфигурацией
  формата. Запасное действие, пишущее `<RECCFG>` программно, не нужно;
- на запись REAPER создаёт один экземпляр — и для всех проходов петли, и
  через паузу. Stop с удалением, undo, дубли, auto-punch и пре-ролл он
  отрабатывает сам по файлу экземпляра;
- экземпляр бывает и без записи: при смене формата у дорожки на записи REAPER
  создаёт его сразу, а на Record уничтожает без сэмплов вместе с файлом.
  Поэтому создание экземпляра дёшево и ничего не включает: дубль начинается
  с первого `WriteDoubles`;
- отказ `CreateSink` срывает всю запись, звук тоже, поэтому экземпляр
  создаётся всегда (D11);
- `PCM_SINK_EXT_GIVE_TRACK_HINT` не приходит: экземпляр не знает своей
  дорожки, и всё нужное ему — в конфигурации формата (D2).

### D2. Настройки камеры живут в конфигурации формата

Конфигурация формата — блок байтов, который REAPER хранит с дорожкой в
`<RECCFG>` и передаёт в `CreateSink` и `ShowConfig`. Первые четыре байта — код
формата `rcam` (`REAPER_FOURCC('r','c','a','m')`): по нему REAPER узнаёт
формат, в списке он называется «Video (camera)». Дальше — версия, устойчивый
идентификатор камеры, её имя для сообщений и режим — ширина, высота и частота
кадров дробью. Экземпляр формата своей дорожки не знает (D1), поэтому всё,
что ему нужно, — здесь.

Окно настроек — форма SWELL из `.rc`, как в `reaper-tabs`. REAPER встраивает
его в своё окно и забирает конфигурацию сообщением `WM_USER + 1024`: сначала
длину, потом байты (`findings.md`, вопрос 1). Без этого окна выбор формата в
Track recording settings не применяется.

Устойчивый идентификатор на Linux — имя ссылки из `/dev/v4l/by-id` (для
встроенной камеры в нём есть серийный номер), а если её нет — из
`/dev/v4l/by-path`. Номера `/dev/videoN` между загрузками меняются
(`camera-capture`).

Почему так: камера дорожки и признак дорожки-камеры хранятся в одном месте, а
сохраняет и восстанавливает их сам REAPER.

Отвергнуто: состояние расширения в дорожке (`P_EXT`) — второе место хранения,
которое пришлось бы согласовывать с форматом.

### D3. Прогрев — по уведомлениям об arm

Поверхность управления (`csurf_inst`) на `SetSurfaceRecArm` и
`SetTrackListChange` пересчитывает множество поставленных на запись
дорожек-камер. Формат записи читается из состояния только у поставленных на
запись дорожек и сверяется с форматом расширения. Реестр устройств держит один
захват на камеру со счётчиком ссылок: первая дорожка открывает камеру,
последняя закрывает. Две дорожки с одной камерой делят один захват
(`camera-recording`).

Экземпляр формата подключается к уже идущему захвату своей камеры на первом
`WriteDoubles`, а не при создании: REAPER создаёт экземпляры и без записи и
уничтожает их без сэмплов (D1). Если захвата нет, например Record нажат сразу
после arm, экземпляр открывает его сам. Начало такого дубля может быть тёмным,
spec это допускает.

Режим записи дорожки-камеры — «выход (моно)», `I_RECMODE` 5
(`findings.md`, вопрос 4). Экземпляр формата REAPER создаёт только дорожке,
которая записывает звук; в режимах выхода физический вход не нужен. Режимы
входа и выхода «с компенсацией задержки» REAPER сдвигает на задержки ввода и
вывода и теряет столько же в конце дубля — при PulseAudio это две секунды.
Выход без компенсации пишется ровно по позициям обработки и заканчивается со
Stop, а моно вдвое дешевле стерео. При постановке на запись расширение само
ставит дорожке-камере этот режим и выключает мониторинг. Ручной работы нет.

Отвергнуто: опрос состояния дорожек по таймеру — лишняя работа 30 раз в
секунду, когда REAPER и так сообщает об изменениях.

### D4. Время файла — время записанного потока, кадры — на ровной сетке

Экземпляр формата считает сэмплы, которые передаёт ему REAPER: время файла
t = n / частота. Кадр номер k стоит в момент t = k / fps. Звук в файл не
пишется.

Каждое место сетки получает кадр, чьё время съёмки, переведённое во время файла
(D5), ближе всего к этому месту. Нет кадра — повторяется предыдущий, лишние
кадры отбрасываются. Кадр, снятый до начала файла, может достаться только
месту 0 — если он к нему ближе всех. Кадры паузы никуда не попадают: для них
нет сэмплов.

Писатель отстаёт от записи примерно на 0.6 с: кадр ставится, когда пары моста
после его момента заполнили полокна (D5). Так у каждого места сетки видны кадры
с обеих сторон, а мост часов интерполирует, а не угадывает вперёд. Это задержка
записи файла, а не синхронности. После Stop обработанное ещё звучит задержку
вывода, и камера снимает кадры последних мест: писатель ждёт их до момента,
когда прозвучал бы конец файла, но не дольше 0.3 с — ждёт главный поток хоста.

Пропуск дольше секунды считается потерей камеры: места сетки получают чёрный
кадр, сжатый один раз при открытии режима (`camera-recording`).

Отвергнуто:

- **Настоящие метки кадров, то есть переменная частота.** Монтажные программы,
  как правило, рассчитывают на ровную частоту, а как её держит REAPER,
  неизвестно.
- **Счёт кадров по номинальной частоте.** Реальная частота камеры отличается от
  номинальной, и расхождение растёт.

### D5. Мост часов — через аудиохук

`OnAudioBuffer` перед обработкой блока кладёт в кольцевой буфер без блокировок
одну запись: монотонное время, позицию обработки блока, слышимую позицию
(`GetPlayPositionEx`), состояние транспорта и длину блока. Больше в звуковом
потоке ничего не происходит: ни блокировок, ни выделения памяти, ни системных
вызовов, кроме чтения монотонных часов.

Рабочий поток переносит записи в историю, по которой писатель каждого дубля
строит мост часов — связь «монотонное время ↔ время файла, которое звучало».
Время файла момента — момент плюс средний сдвиг «время файла − монотонное» пар
в окне 1 с вокруг него, без пар дальше четырёх медианных отклонений; наклон
— 1. Окно короткое и стоит вокруг момента: так оно усредняет дрожание пачек и
отслеживает и расхождение часов звуковой карты и системных (`recording-sync`;
за окно это доли миллисекунды), и медленное блуждание слышимой позиции хоста
(`findings.md`, задержка вывода).

Пары для моста — из сопоставления блоков экземпляра с блоками аудиохука
(`findings.md`, вопрос 7). Позиция из `SETCURBLOCKTIME` — та же
`GetPlayPosition2Ex`, что видит аудиохук у этого блока; блоки экземпляра идут
в том же порядке, что блоки записи аудиохука, один к одному. Блок экземпляра
сопоставляется со следующим блоком записи аудиохука с той же позицией: по
одной позиции нельзя — в петле она повторяется каждый проход, после паузы
откатывается назад. Пара моста — отметка аудиохука и время файла, которое
звучало в этот момент: счёт сэмплов экземпляра на начало блока минус разница
«позиция обработки − слышимая позиция» этого блока. Время вызова
`WriteDoubles` для часов не годится: REAPER зовёт его из рабочих потоков
пачками, с отставанием от звукового потока до 40 мс.

Связь рвётся на паузе: во время паузы сэмплов нет, а монотонное время идёт.
Разрыв виден по паре, далёкой от прямой больше чем на 0.3 с, — и мост после
него строится заново по новым парам. Кадры во время паузы никуда не ложатся:
для них нет сэмплов (D4). После начала записи и после паузы хост держит
слышимую позицию на месте, пока звук не дошёл до выхода, — такие пары в мост не
идут.

Поправка на задержку звука. Дорожка-камера пишет выход без компенсации (D3):
блок обработан на позиции P, а слышно его на задержку вывода позже. Задержку
сообщает хост — слышимой позицией у каждого блока: разница «позиция обработки
− слышимая» и есть его задержка вывода в этот момент (`recording-sync`: «по
значениям, которые сообщает REAPER»). Снимок `GetInputOutputLatency` при
создании экземпляра не годится: при PulseAudio задержка за дубль меняется на
десятки миллисекунд (`findings.md`, задержка вывода). Направление поправки
известно, поэтому она применяется.

Монотонные часы на каждой ОС те же, что у меток кадров её API камер:
`CLOCK_MONOTONIC` на Linux, QPC на Windows, host time на macOS.

### D6. Время съёмки на Linux — из метаданных UVC

Захват — V4L2 в потоковом режиме с отображением буферов в память, MJPEG в
выбранном режиме, монопольно.

Время. Параллельно с видео открывается узел метаданных камеры. Если в
заголовках есть PTS и SCR, расширение само восстанавливает связь часов камеры с
монотонными и берёт начало съёмки кадра в `CLOCK_MONOTONIC`. Связь — нижняя
огибающая пар «SCR — момент, когда хост обработал пакет»: пакет не бывает
обработан раньше, чем передан. Номер кадра шины USB для связи не годится, хотя
драйвер при `hwtimestamps=1` строит её именно через него: камера ноутбука
нумерует кадры шины своим счётчиком со случайным сдвигом от сеанса к сеансу
(`findings.md`, время съёмки). Если PTS или SCR нет, или связь неустойчива
(часы камеры вне разумного, задержка обработки разбросана шире 20 мс, время
съёмки не раньше прихода буфера), берётся метка буфера без поправки
(`camera-capture`, `recording-sync`).

Отвергнуто:

- **`hwtimestamps=1`.** Нужен root, и поведение драйвера меняется для всех
  программ.
- **libavdevice.** Не читает узел метаданных.
- **GStreamer или PipeWire.** Тяжёлые зависимости, и заголовков UVC они не
  отдают.

### D7. MJPEG как есть и собственный писатель контейнера

Кадры пишутся в том виде, в каком пришли. Камеры UVC часто опускают в кадрах
таблицы Хаффмана. Такой кадр дополняется стандартными таблицами (приложение K
стандарта JPEG), чтобы его прочли и декодеры, которым нужен полный JPEG. Сжатые
данные изображения не меняются (`camera-capture`).

Контейнер пишет своя библиотека: одна дорожка MJPEG, ровная частота, кадры
только в конец. Выбран **фрагментированный QuickTime (MOV) с кодеком
Photo-JPEG** (`findings.md`, вопрос 6):

- в начале файла — индекс без кадров, дальше фрагменты `moof` + `mdat` по
  секунде. На Linux его открывает FFmpeg, на macOS, насколько известно, —
  AVFoundation, через которую REAPER там по умолчанию показывает видео;
  проверка на macOS — вместе с её захватом;
- после каждого целого фрагмента писатель обновляет длительности в индексе
  (`mvhd`, `tkhd`, `mdhd`, `mehd`). REAPER берёт длину фрагментированного файла
  из индекса и фрагменты не пересчитывает: без этого файл, оборванный
  аварией, открывается видео нулевой длины, а с этим — видео до последнего
  целого фрагмента. Это единственная правка уже записанного: кадры идут только
  в конец.

Все три кандидата разведки REAPER на Linux открыл как видео правильной длины.
Отвергнуты:

- **MOV с индексом в конце.** Оборванный аварией файл не читается вовсе.
- **Matroska.** Оборванный файл REAPER открывает с выдуманной длиной (30 с),
  а на macOS её, насколько известно, не открывает AVFoundation.
- **libavformat.** На Windows и macOS это FFmpeg, которого у пользователя может
  не быть, а spec запрещает требовать доустановку.

### D8. Потоки и защита звука

- Звуковой поток — только аудиохук (D5).
- Поток захвата — один на камеру.
- `WriteDoubles` экземпляра формата REAPER зовёт из своих рабочих потоков,
  каждый раз из любого (`findings.md`, вопрос 7), а `GetLength` — из главного,
  одновременно с ними. `WriteDoubles` всё равно пишется так, как если бы его
  звали из звукового потока: он только считает сэмплы и ставит событие в
  очередь без блокировок. Счётчик сэмплов — атомарный.
- Поток писателя — один на запись: выбирает кадры для мест сетки и пишет на
  диск.
- Главный поток — поверхность управления, окна, сообщения.

Очереди ограничены. Если писатель отстаёт, теряются кадры видео, а не звук:
`WriteDoubles` никогда не ждёт. Процессор занят только копированием: видео не
кодируется и не декодируется, кроме однократного сжатия чёрного кадра.

### D9. Раскладка кода и кроссплатформенность

| Цель | Что в ней | От ОС и REAPER |
|---|---|---|
| `cam_timing` | мост часов, сетка кадров | не зависит |
| `cam_container` | писатель контейнера, дополнение таблиц JPEG | не зависит |
| `cam_capture` | интерфейс источника кадров, реестр устройств, тестовый источник | не зависит |
| `cam_capture_v4l2` | захват Linux: V4L2 и метаданные UVC | только Linux |
| `reaper_cam` | модуль расширения: формат, поверхность управления, аудиохук, окна | REAPER |

Независимость первых трёх целей проверяется по тексту исходников, как в
`reaper-tabs` (`CheckIsolation`): заголовки ОС и SDK REAPER в них запрещены.
Ветки CMake для Windows и macOS сохраняются по образцу `reaper-tabs`, но модулей
захвата для них в этом изменении нет, и сборка там не проверяется.

### D10. Разведка на тестовом источнике — первой

Тестовый источник рисует на кадре время файла и позицию шкалы, на которую кадр
должен лечь по расчёту расширения. Рисует LICE, сжимает jpeglib из WDL. В окне
видео REAPER видно, совпадает ли нарисованная позиция с курсором
воспроизведения, — в каждом режиме записи. Так без камеры проверяется вся
цепочка D1, D4 и D5.

Вопросы разведки:

1. Появляется ли формат в Track recording settings, и работает ли программное
   назначение через `<RECCFG>`.
2. Вызывается ли `SETCURBLOCKTIME` при записи, и какие позиции приходят при
   pre-roll, count-in и в петле.
3. Что приходит в экземпляр при паузе, auto-punch и в петле: один экземпляр на
   запись или новый на каждый проход, идут ли сэмплы во время паузы.
4. При каком режиме записи дорожки REAPER создаёт экземпляр без физического
   входа, и как ставит айтем относительно записанных сэмплов — с поправкой на
   задержки или без.
5. Что делает REAPER, если экземпляр не создался: прерывает всю запись или
   пропускает дорожку. От ответа зависит D11.
6. Какой контейнер из D7 REAPER на Linux открывает как видео-айтем правильной
   длины.
7. Из какого потока REAPER зовёт `WriteDoubles`.

Ответы записаны в `findings.md` изменения, и по ним поправлены D1, D3, D5,
D7, D8 и D11.

Тестовый источник остаётся для автотестов и живых проверок. Пользователю он не
показывается: он есть только в отладочной сборке.

### D11. Ошибки камеры

Отказ `CreateSink` REAPER не переживает: запись не начинается вовсе, звук
тоже не пишется, а в окне ошибки — общее «Can't write to recording files»
без причины из `SetRenderLastError` (`findings.md`, вопрос 5). Поэтому
экземпляр создаётся всегда. Если камера недоступна, места сетки получают
чёрный кадр, а причина с именем камеры уходит в консоль REAPER. Запись звука
не прерывается (`camera-recording`).

Потерю камеры во время записи поток захвата видит по ошибке устройства или по
молчанию дольше секунды. Реестр помечает камеру потерянной, места сетки получают
чёрный кадр, в консоль уходит одно сообщение на дубль. Во всех сообщениях —
имя камеры из конфигурации.

## Risks / Trade-offs

- [Камера не присылает PTS и SCR или присылает мусор] → метка буфера без
  поправки, spec это допускает; проверки устойчивости связи часов отбрасывают
  выбросы.
- [Кадры без таблиц Хаффмана не читаются частью декодеров] → дополнение
  стандартными таблицами (D7).
- [Контейнер не проверен в REAPER на Windows и macOS] → проверка переносится в
  изменение с их захватом, там же пересматривается выбор контейнера.
- [Пока дорожка-камера на записи, камеру не получат браузер и другие программы]
  → ограничение монопольного V4L2; совместный доступ через PipeWire вне scope.
- [Файлы большие: порядка 10 ГБ в час при 720p] → цена MJPEG без
  перекодирования, выбранного ради малой нагрузки на процессор.
- [Расширение само меняет режим записи и мониторинг дорожки-камеры] → меняется
  только дорожка-камера, звук на ней всё равно не нужен.
- [Пользователь поставит дорожке-камере вход или выход с компенсацией
  задержки] → при arm расширение возвращает режим «выход (моно)» (D3); иначе
  конец каждого дубля терялся бы на задержку ввода и вывода.
- [Формат виден и в других окнах REAPER со списком форматов, например в
  Render] → там экземпляр записал бы камеру вместо сведения; поведение в
  Render разведка не проверяла — проверяется при реализации окна настроек
  (задача 6.5).
- [Модальные окна REAPER во время проверок] → живые проверки останавливают
  запись действием 40667 «Stop (save all recorded media)»: у пользователя
  включено окно «Select files to save or delete» после Stop.
